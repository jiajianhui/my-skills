# Git 提交规范

这个 skill 用于执行代码提交，目标是让提交过程稳定、可复用、符合固定格式。

## 触发场景

当用户表达以下意图时使用：

- 提交代码
- 帮我提交
- commit 一下
- 按规范提交
- 用固定格式提交

## 默认流程

1. 先检查 `git status --short`，确认工作区范围。
2. 如果用户只说“提交代码”，先查看 `git diff` 判断提交类型：普通功能/修复提交，或 release 提交。
3. 只暂存与当前提交意图直接相关的文件，不顺手提交无关变更。
4. 可以查看 `git diff` / `git diff --staged` 来确认提交内容，但不要修改代码、格式化代码、补 bug 或整理文件。
5. 如果提交前发现明显问题，可以先用简短消息提示用户；除非用户明确要求修复或暂停，否则继续按当前代码提交。
6. 再执行 `git commit`。
7. 返回提交信息和 commit hash。

## 提交信息规则

默认使用中文提交信息，简洁、直接，描述本次变更的核心动作。

文件名、函数名、模块名、类名等代码内原始标识符默认不要翻译。
提交信息应保留这些原始名称，只用中文描述动作。

例如：

- 用 `完善newsService代码注释`，不要写 `完善新闻服务代码注释`
- 用 `调整readLatestDigest返回结构`，不要写 `调整读取最新摘要返回结构`
- 用 `优化git-commit-style skill规则`，不要写 `优化Git提交规范技能规则`

默认格式：

`<type>: <中文提交说明>; 由AI提交🌟`

示例：

- `docs: 补充关键文件注释和贡献说明; 由AI提交🌟`
- `feat: 新增新闻抓取结果缓存接口; 由AI提交🌟`
- `fix: 修复 RSS 解析异常处理; 由AI提交🌟`
- `refactor: 清理未使用参数并简化解析流程; 由AI提交🌟`

## 类型选择规则

- `feat`：新增功能
- `fix`：修复缺陷
- `docs`：文档、注释、README、AGENTS 等说明性改动
- `refactor`：重构或清理代码，不改变功能
- `style`：纯格式调整，不改逻辑
- `test`：测试相关变更
- `chore`：配置、依赖、脚本或其他杂项维护

## 提交约束

- “提交代码”只代表执行提交流程，不代表允许修改代码；提交前不要做任何源码修复、格式调整、依赖更新或生成文件变更。
- 不提交 `node_modules/`、IDE 配置、缓存文件或其他本地产物，除非用户明确要求。
- 不默认把所有改动一次性提交；只提交与当前需求相关的内容。
- 如果发现存在无关修改，要主动避开，必要时明确指出。
- 如果发现明显的编译风险、遗漏文件、冲突标记、调试代码等问题，可以在提交前简短提示；除非用户明确要求处理，否则不要改代码，继续提交已确认范围。
- 如果用户明确给了提交内容，优先使用用户提供的描述，并补全前缀类型与尾缀 `; 由AI提交🌟`。
- 如果用户没有指定类型，则根据改动内容自动选择最合适的类型。


## Release 提交流程

当用户表达以下意图时，也使用本 skill：

- 发新版本
- 提交版本号
- bump version
- release commit
- 打 tag
- 生成版本更新说明

默认采用轻量方案 A：`release commit + git tag`。

自动判断规则：

- 当用户只说“提交代码”时，如果工作区只包含版本号、构建号、App Store/TestFlight 更新说明、CHANGELOG、Release Notes 等发版元数据变更，则按 release 提交流程处理。
- 如果工作区同时包含业务代码、UI、资源、配置逻辑、测试等普通开发变更，则按普通提交流程处理，不自动打 tag。
- 如果 diff 同时包含版本号变更和业务代码变更，先提示用户拆分；默认只提交普通开发变更，不把它们混成 release commit。
- 如果无法确定版本号变更是否属于发版，先用一句话说明不确定点，并按普通提交流程继续，除非用户明确说这是新版本。

推荐流程：

1. 先检查 `git status --short`，确认工作区是否只有版本号、构建号、发布说明等发版相关变更。
2. 查看最近提交和 tag：`git log --oneline --decorate -n 10`、`git tag --sort=-creatordate | head`，确认上一个版本和本次版本关系。
3. 如果用户要求“发版”但还没有改版本号，可以按项目现有位置修改版本号/构建号；如果不确定版本文件位置，先搜索并确认。
4. release commit 的默认提交信息使用：`💎新版本——<version>`，保持本仓库历史风格。
5. release tag 的默认格式使用：`v-<version>`，例如 `v-1.1.4`，保持本仓库现有 tag 风格。
6. tag 应打在 release commit 上；如果本次没有 release commit，必须先向用户说明并确认是否直接给当前 HEAD 打 tag。
7. 完成后返回 release commit hash、tag 名称，以及本次版本包含的主要变更摘要。

约束：

- 不把普通功能改动混入 release commit；release commit 只包含版本号、构建号、发布说明等发版元数据。
- 不自动 push，除非用户明确要求推送 main 或 tags。
- 不自动上传 App Store / TestFlight，除非用户明确要求。
- 如果本次版本号低于或等于最近 tag，先停止并提示风险。


## 输出方式

提交完成后，简洁返回：

- 实际提交信息
- commit hash

不要展开冗长总结，除非用户要求。
