# 学习文档写作

写出让读者能够理解、操作和复习的学习材料。这个 skill 提供判断标准，不提供必须照抄的文章模板。用户明确提出的写作标准、项目事实和当前疑问优先于默认方法。

## 先弄清当前任务

写作前确认：

- 读者已经学过什么，现在卡在哪里，读完后下一步要做什么。
- 当前文档主要承担概念解释、实操跟练、项目路线、复习、排错、练习或方案对比中的哪一种职责。
- 目录入口、相邻章节、真实代码和项目阶段怎样衔接，避免孤立修改一篇文档。
- 哪些内容是当前必需，哪些应放到后续章节或直接省略。

文档角色只用于帮助判断内容，不要在正文中机械宣布“本文角色”，也不要让所有角色使用同一套开头、结构和结尾。

## 使用一条自然主线

根据内容选择最容易理解的组织方式，例如：

```text
输入 -> 处理 -> 输出
页面 -> 后端 -> 数据库
先认识 -> 再运行 -> 最后扩展
当前条件 -> 方案差异 -> 选择
阶段目标 -> 实现 -> 验收
```

整篇围绕一条主要问题推进。统一业务场景能帮助理解时就持续使用；换例子更清楚时，不要为了形式统一硬套同一个场景。

不强制每篇文章都先放知识地图、三个问题、流程图或全文小结。只有当读者确实需要先看全貌时才给地图；一句话能说清的关系不要画图或建表。

## 先说人话，再补术语

- 优先写清“谁做什么、使用什么、得到什么”，少用“进行处理”“完成衔接”“真正决定它是什么”等抽象句式。
- 代词和概念必须有明确指向。读者可能追问“它是谁”“等什么”“这是哪里的数据”时，直接补全主语、动作和结果。
- 新术语第一次出现时用一句人话解释。具体例子已经能说明问题时，先看例子，再给名称。
- 解释要完整：不要只说“两个操作都要等待”，要说明各自在等待什么、分别得到什么。
- 用户已经对某句话表示困惑时，把它当作表达层级不对的证据，重写或删除，不要为原句辩护。
- 少写“这里只需要记住”“真正需要掌握”“阅读架构选读”等课程腔。直接说明要做什么，或者说“可以按需阅读，不影响后续练习”。

不要预防所有可能的误解。明显常识、与当前操作无关的安全提醒、暂时不会遇到的底层过程和边界情况，不要为了显得完整而加入正文。必要警告必须具体说明风险发生在哪里。

## 控制深度，而不是只控制长度

- 先讲正常流程，再讲当前练习会遇到的失败；罕见边界放到排错章或后续章节。
- 一个段落必须帮助读者理解当前问题、完成操作或判断结果，否则删除。
- 概念技术上正确，不代表此刻必须解释。保留能够区分相邻概念和继续操作的最小信息。
- 新概念和重点不能一笔带过；复杂到会打断当前主线时，再拆成独立章节。
- 不要把完整概念章压成提纲，也不要把短过渡章扩写成手册。

精简优先删除重复、抽象铺垫、防御性说明和过早展开的细节，不要删除关键动作、真实示例和判断成功的方法。

## 让代码和解释严格对齐

- 示例使用当前项目真实的文件名、路径、字段、接口结构和依赖版本。
- 正文只解释代码实际出现或当前步骤实际使用的属性和行为。示例没有展示 `status`、`ok` 或 `headers`，正文就不要突然逐项讲它们。
- 概念章使用能证明当前结论的最小代码；实操章必须提供完成当前步骤所需的上下文和命令。
- 代码后只解释不容易直接看出的输入、动作和结果，不逐行翻译字面意思。
- 明确区分伪代码、简化示例和可以复制到真实项目的代码，避免让读者误以为示例是本地 mock 或项目现状。
- 前端、后端和数据库之间的数据转换要落到实际代码，例如 `JSON.stringify(values)`、`request.body` 和 `response.json()`，不要只说“对象穿过 HTTP”。

## 技术选型也属于学习设计

选择框架、库或实现方式时，同时考虑：

- 当前章节要建立的基础概念。
- 后续真实项目需要的工程能力。
- 用户的学习目标、求职目标和已经确认的技术路线。
- 当前社区和公司常用方案，以及官方推荐和版本现状。
- 新工具会不会同时引入过多无关概念。

不要因为原生方案依赖更少，就自动认为它最适合整条学习路线。可以先用原生能力理解基础，再在真实项目中练习常见封装；也可以让两个递进项目分别使用基础方案和常用工具，但要明确这是教学安排，不是 UI 框架的限制。

区分不同层级的工具。例如请求客户端负责发送 HTTP，请求状态库负责缓存、同步和重新请求；后者通常不会取代前者。做比较时只比较同一层的问题。

涉及当前版本、生态现状、招聘相关性或“最流行”判断时，先核对最新官方资料和可靠数据，再做选择。

## 处理章节之间的关系

- 前一章已经讲清的内容，后文直接使用；后一章才实现的内容，只说明衔接，不提前复制教程。
- 项目总览维护阶段、范围和验收；知识章解释概念；实操章写修改位置、代码、命令和检查点。
- 一个概念只完整解释一次。其他章节用准确链接和一句衔接语带过。
- 并列项目要保持业务范围、API contract 和完成标准一致。为了学习而使用不同工具时，保持对外请求函数职责相近，并在最终比较中把 UI 差异与工具差异分开。
- 修改章节编号、文件名或路线后，同步目录、相邻章节和所有相关链接。

## 优化现有文档

优化不是先润色句子，而是先判断问题属于哪一类：

```text
表达不清：缺少明确对象、动作或结果
逻辑跳跃：前后步骤之间缺少连接
示例失配：正文解释了代码中没有的内容
深度失衡：简单问题讲到底层，重点反而略过
路线失衡：技术选型没有服务整体学习目标
```

处理顺序：

1. 逐条理解用户反馈指向的真实困惑，不只替换被点名的词。
2. 删除没有价值的段落；需要保留时，用最短的具体说法重写。
3. 检查相邻段落和章节，修复同一问题的旧表述，但不顺手扩大到无关内容。
4. 连续阅读修改后的内容，确认读者不需要依赖补充解释才能看懂。
5. 保留用户已经确认的节奏、术语和项目决定。

## 完成前检查

- 读者能否明确说出谁做什么、数据从哪里来、最后得到什么？
- 是否存在看似正确但当前无用的解释、提醒或术语？
- 代码展示的内容和正文解释的内容是否一一对应？
- 重点和新概念是否讲够，普通步骤是否足够简洁？
- 技术选型是否服务完整学习路线，而不只是局部实现最省事？
- 是否与目录、相邻章节、真实项目和已有代码一致？
- 标题层级、链接、路径、命令和代码块是否正确？

最终目标不是让文档看起来结构完整，而是让读者第一次阅读就明白，能够继续操作，并在复习时快速找回主线。
