# 技术学习文档写作

写出让读者能够理解、操作和复习的学习材料。这里提供的是写作判断标准，不是固定模板；用户明确提出的写法、项目事实和已有决定优先。

## 先确认文档承担什么任务

写作或修改前先弄清：

- 读者已经学过什么、现在卡在哪里、读完后要继续做什么。
- 当前内容主要负责概念解释、项目跟练、排错、复习、路线规划、方案比较还是练习。
- 相邻章节、目录入口、真实代码和项目阶段怎样衔接。
- 哪些内容是本次目标必需的，哪些应留给后续章节或直接删除。

文档角色只用于帮助判断写法，不要在正文中机械宣布分类。项目中的字段、路径、依赖、接口和完成阶段以仓库现状为准，不凭记忆补全。

## 先建立主线，再设计标题

整篇围绕一个主要问题推进。根据内容选择最容易理解的关系，例如：

```text
输入 -> 处理 -> 输出
页面 -> API -> 数据库
当前状态 -> 完成一条链路 -> 验证结果 -> 扩展
使用场景 -> 方案差异 -> 选择与代价
阶段目标 -> 前置条件 -> 实现任务 -> 验收
```

不同文档可以采用不同主线：

- 概念文档通常从真实问题或例子进入，再解释机制、边界和使用位置。
- 实操文档从当前可运行状态出发，逐步形成可验证的功能链路。
- 学习路线说明阶段目标、依赖、交付物和验收，不把它写成概念大全。
- 方案比较先固定场景和比较层级，再给选择，不比较职责不同的工具。

这些是可选方向，不是必须照抄的章节模板。只有总览能明显降低理解成本时才画地图或流程图；一句话能讲清就不要增加结构。

## 实操跟练使用最小完整步骤

实操步骤按“可验证的业务结果”划分，不按代码行数、文件数量或最终文件结构机械拆分。一个步骤可以同时修改几个位置，只要这些修改共同完成同一条链路。

合适的步骤应当：

- 从上一步可运行状态出发，结束时能够执行一个真实动作并看到结果。
- 新增代码通常会继续留在后续实现中，不依赖下一步马上删除的空壳、占位内容或临时页面。
- 只引入当前链路需要的状态、类型、属性和请求函数；新问题出现时再补对应内容。
- 让读者能说清本步增加了什么、数据经过哪里、页面最终发生什么变化。

步骤过大时，读者只能复制一份最终代码，却说不清其中有几条链路；步骤过小时，只完成“打开空容器”“显示临时文字”等没有业务结果的动作。两种情况都要重新划分。临时代码只有在它能独立验证一个不确定或高风险前提时才值得加入，并要明确说明验证目标和清理位置。

正常情况下先跑通主流程，再补完整反馈：

```text
最小可用链路 -> 相邻业务链路 -> 加载、错误和成功反馈 -> 最终代码对照
```

如果缺少错误处理会让当前示例本身错误或产生误导，就在当前步骤处理，不要为了形式强行后置。服务后续的设置只有在当前已经真实使用、能减少无意义返工时才提前保留，并说明它此刻的作用。

每个步骤结尾给出与本步对应的验证动作。较长的最终文件放在分步实现之后，供对照或复制，必要时折叠展示；最终代码不能替代前面的学习顺序。

## 让代码、解释和数据流严格对齐

- 使用项目真实的文件名、路径、字段、接口结构和依赖版本。
- 代码前说明修改位置和本步目标；代码后解释不容易直接看出的输入、状态变化和结果，不逐行翻译字面意思。
- 新的回调形参、组件属性或返回值第一次影响理解时立即说明。命名应体现角色，例如含义不清时用 `currentArticles`，不要只写 `current`。
- 正文只解释代码实际出现或当前步骤实际使用的内容，不提前讲尚未接入的属性和边界。
- 跨前端、后端和数据库的数据流要落到真实转换，例如表单值怎样进入请求体、后端怎样读取、响应怎样更新页面状态。
- 明确区分伪代码、局部修改片段、简化示例和可以完整复制的代码。局部片段要说清是新增、替换还是保留其余内容。
- 概念示例使用能证明结论的最小代码；实操示例提供完成当前结果所需的上下文和命令。

## 控制解释深度

- 先讲正常流程，再讲当前练习真正会遇到的失败；罕见边界放到排错内容或后续章节。
- 先说清谁使用什么、做了什么、得到什么，再补术语。
- 主语和代词必须有明确指向。读者可能追问“它是谁”“等什么”“这是哪里的值”时，直接补全对象和动作。
- 重点和新概念要讲够；显而易见的语法、暂时无关的底层细节和防御性提醒不要为了完整而展开。
- 用户对一句话表示困惑时，把它视为表达层级或上下文有问题，重写或删除，不为原句辩护。

精简时优先删除重复铺垫、抽象套话、过早展开的边界和没有操作价值的段落，不删除关键动作、真实例子和判断成功的方法。

## 保持章节、项目和学习路线一致

- 前文已经完整解释的内容，后文直接使用；后续才实现的能力只做衔接，不提前复制教程。
- 项目总览维护阶段、范围和验收；知识章解释概念；实操章说明修改位置、代码、命令和检查点。
- 一个概念只完整解释一次，其他位置使用准确链接和一句衔接。
- 修改标题、编号、文件名、阶段或 API contract 后，同步目录、相邻章节、示例代码和相关链接。
- 并列项目保持业务范围和完成标准一致；为了教学使用不同工具时，明确哪些差异来自 UI，哪些来自工具。

技术选型也是学习设计。选择工具时同时考虑当前要建立的基础、后续项目需要的工程能力、用户的学习目标和新工具带来的额外概念。比较时只比较同一层职责；涉及版本、生态现状或招聘相关性时先核对最新资料。

## 优化现有文档

先判断问题类型，再修改文字：

```text
主线不清：章节没有围绕同一个问题推进
步骤失衡：终局代码提前倾倒，或动作被拆得过碎
解释失配：正文、代码和项目现状不一致
深度失衡：普通步骤展开过多，真正重点反而略过
路线失衡：内容与前后章节、项目阶段或学习目标脱节
```

处理顺序：

1. 逐条理解用户反馈指向的真实困惑，并检查相邻段落、章节和真实代码。
2. 先修主线、步骤和内容范围，再润色句子。
3. 删除无价值内容；需要保留时，用最短的具体说法重写。
4. 连续阅读修改后的完整段落，确认读者不依赖额外解释也能继续操作。
5. 保留用户已经确认的节奏、术语、项目决定和现有改动。

## 完成前检查

- 读者能否说清当前问题、数据流和最终结果？
- 每个实操步骤是否形成可验证结果，既没有提前倾倒终局代码，也没有用完即删的过渡代码？
- 代码、正文、文件路径、接口和项目阶段是否一致？
- 新形参、属性和关键状态是否在第一次影响理解时得到说明？
- 重点是否讲够，普通步骤是否保持简洁？
- 是否存在重复解释、抽象套话、过早展开的边界或当前无用的提醒？
- 章节与目录、相邻内容和完整学习路线是否衔接？
- 标题层级、链接、命令和代码块是否正确？

最终目标不是让文档看起来面面俱到，而是让读者第一次阅读就能理解并完成操作，之后复习时也能快速找回主线。
