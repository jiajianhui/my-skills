# 学习文档写作

帮助读者建立可以复述、操作和验证的知识地图。不要把“写得短”当成唯一目标；先保住理解所需的结构，再删除重复和当前阶段用不到的细节。

## 先判断文档角色

写作前先选择一种主要角色，不要把所有内容套进同一模板：

| 文档角色 | 主要任务 | 默认收口方式 |
|---|---|---|
| 阅读导引 | 建立全局地图、学习顺序和章节边界 | 阅读路线与完成标准 |
| 概念章节 | 讲清一个问题、相关概念及其职责关系 | 放回统一场景中理解 |
| 实操章节 | 把已学概念组合成可运行结果 | 检查点与完成标准 |
| 复习笔记 | 把详细内容重新串成一条短主线 | 回看导航 |
| 决策对比 | 根据条件判断不同方案适合什么场景 | 选择问题或决策规则 |
| 速查与排错 | 根据现象快速定位概念、文件或层级 | 查找表或排查顺序 |
| 项目路线 | 安排阶段、范围、交付结果和依赖 | 分阶段验收 |
| 练习题 | 用回忆、判断和操作验证理解 | 答案线索与回看位置 |

如果一篇文档同时承担多种角色，先确定主要角色；其他角色只作为辅助部分出现。

## 写作前先核对上下文

1. 判断读者已经学过什么、当前要解决什么问题。
2. 检查目录入口、相邻章节、项目阶段和对应代码，避免孤立判断一篇文档。
3. 以用户已经确认的范围和真实代码为准，不写课程或项目中没有实际使用的实现。
4. 标出哪些是当前必学、后续再学、按需查看或明确不做的内容。
5. 涉及版本、命令、框架行为和安全做法时，使用官方资料核对；文案仍围绕当前项目，不扩写成资料汇编。

## 建立唯一的组织主线

根据主题选择一种最自然的主线：

```text
执行流程：输入 -> 处理 -> 输出
职责关系：页面 -> 后端 -> 数据库
学习层次：先认识 -> 再运行 -> 最后扩展
变化过程：原来怎样 -> 增加什么 -> 现在怎样
决策过程：当前条件 -> 可选方案 -> 最终选择
项目阶段：交付结果 -> 关键实现 -> 验收
```

不要为了符合模板，强行把所有主题写成时间顺序。真正要求是整篇只有一条主要组织线，每个主要小节都在推进它。

能使用统一业务场景时，贯穿使用同一个例子。不要每解释一个概念就换一套业务背景。跨章节材料要让同一条请求、同一份数据或同一个项目逐步增加能力。

## 先给地图，再补必要细节

开头先回答：

```text
这篇解决什么困惑？
它位于完整学习或执行流程的哪一段？
读完能做到什么？
```

然后给出主线、职责图或最小结论，让读者先知道后面为什么这样展开。

每个关键步骤至少说清：

```text
对象是什么
做了什么
得到什么
```

在容易混淆时，再补“为什么需要”和“与相邻概念有什么区别”。不要强制每个知识点都补齐定义、原因、写法、示例和误区。

## 控制学习深度

- 先讲正常主线，再讲错误、边界和工程扩展。
- 先完成当前阶段需要的最小闭环，再把进阶内容标成后续或选读。
- 第一次出现术语时，用一句人话解释；后文直接使用，不重复定义。
- 容易混淆的概念放在一起比较，不分散到多个章节反复解释。
- 复杂内部过程只保留当前读者需要认识的层级；已经有详细章节时，复习文档只保留入口、关键节点和终点。
- 安全、数据完整性和破坏性操作不能为了简短而省略必要警告。

精简后不能只剩抽象结论。至少保留区分相邻概念、继续操作和判断结果所需的信息。

## 保持具体

- 优先写真实文件、命令、请求、输入、输出和检查位置。
- 抽象概念后立刻落到当前项目中的对象。
- 避免只写“负责配置”“进行处理”“完成连接”“驱动两边”等空泛说法。
- 用“谁使用它、它读取什么、它产生什么”描述工具或文件职责。

不要只写：

```text
prisma.config.ts 负责 Prisma 的相关配置。
```

应该写成：

```text
prisma.config.ts 告诉 Prisma CLI：Schema 在哪里、迁移记录放哪里、要连接哪个数据库。
```

## 根据角色控制代码示例

- 概念章节使用最小示例，只保留证明当前概念所需的代码。
- 实操章节提供足以完成当前步骤的真实代码和命令，不要为了短而省略关键上下文。
- 复习笔记只保留能唤起完整流程的代表性代码。
- 项目路线写交付结果和关键实现，不提前塞入整段实现代码。
- 示例必须与当前项目的文件名、路径、类型、接口契约和依赖版本一致。

代码之后只解释读者不容易直接看出的职责、输入输出和关键语法，不逐行翻译代码字面意思。

## 正确选择表达形式

- 有明确先后顺序时使用短流程。
- 多个对象需要逐项对照时使用表格。
- 表结构、目录或层级关系使用小型树状结构。
- 只有一个事实时直接写一句话，不为它创建图表。
- 流程图、表格和正文不要连续表达同一组信息。

图表要帮助读者看见关系，不要用来装饰页面。

## 处理章节之间的关系

先给当前章节一个明确合同：它负责讲什么，不负责讲什么。

- 前一章已经完整解释的内容，只说明怎样在本章继续使用。
- 后一章才实现的内容，只说明衔接关系，不提前展开实现。
- 详细章节负责解释和练习；复习章节负责重新组织，不复制详细步骤。
- 概念章节回答“是什么、为什么、怎样判断”；实操章节回答“改哪里、执行什么、检查什么”。
- 项目路线只维护阶段、范围和验收，不重复知识章节的教程正文。

跨文档保持术语、阶段、接口、文件名和示例数据一致。发现旧描述与当前代码或用户决定冲突时，先以当前事实为准，再修正文档。

## 避免重复和阅读疲劳

- 一个概念只完整解释一次，后文直接引用或使用。
- 相邻段落表达同一结论时，保留更具体、更接近操作的一处。
- 代码、表格或流程已经说清楚的内容，不再换一种形式复述。
- 长调用链只保留学习当前主题所需的层级。
- 小标题必须承担导航作用，不为一两句普通说明机械拆节。
- 连续出现多个列表、表格或代码块时，用短句说明它们之间的推进关系。
- 小结只有在能够重建知识地图时才保留，不把全文再说一遍。

## 各类文档怎样收口

### 概念章节

用统一场景重新串一次核心关系，并说明下一步会在哪里用到。不要增加新的概念。

### 实操章节

优先给检查点或完成标准：能否运行、能否操作、能否解释、能否验证。必要时列出本轮明确不做的内容。

### 复习笔记

使用简短回看导航。读者卡在哪个概念，就知道回到哪一节。

### 项目路线

每个阶段写清：开始前回看什么、交付什么、关键实现是什么、怎样验收。范围边界只维护一份。

### 练习题和排错文档

题目或现象应能指回具体章节、层级、文件或检查步骤，不只提供孤立答案。

## 优化现有文档

1. 先判断文档角色和唯一主线，不急着逐句润色。
2. 标出每一节在主线中的作用；没有作用的内容删除、后移或放到更合适的章节。
3. 合并重复说明，补齐跳跃处缺少的对象、动作或结果。
4. 保留系统文档已有的知识地图、统一示例、边界说明、真实练习和验收标准。
5. 借鉴复习文档的轻快节奏，但不要把完整概念章或实操章压成提纲。
6. 修改后连续阅读相邻几节，检查是否出现“局部更短，整体反而断裂”。
7. 只修改当前目标相关内容，不顺手重写标题、章节结构或无关章节。

## 完成前检查

- 开头是否清楚说明问题、位置和阅读结果？
- 全文是否只有一条主要组织线？
- 每节是否提供了新的理解或操作结果？
- 概念是否落到了真实场景、文件或数据？
- 是否区分了当前必学、后续再学和不做内容？
- 示例是否与真实项目和当前版本一致？
- 是否有同一信息被正文、表格、流程和小结重复表达？
- 实操是否说明如何检查成功，项目阶段是否有验收标准？
- 精简后是否仍然具体，完整后是否仍然读得动？

最终目标不是让读者背下全部内容，而是让读者能说清主线，知道下一步做什么，并在卡住时找到正确位置。
