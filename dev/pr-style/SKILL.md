# PR 文案规范

这个 skill 用于创建 PR 或撰写 PR 标题/正文，让 PR 内容像工程师手写，而不是套模板。

## 默认流程

1. 先检查当前分支、目标分支、提交记录和 diff，确认 PR 范围。
2. 如果分支尚未推送，先推送当前分支。
3. 创建 PR 前检查是否已有同 head/base 的 PR，避免重复。
4. 根据实际 diff 写标题和正文，正文默认只保留 `## 变更内容`。
5. 小改动也使用统一正文格式，但条目保持简短。

## 标题规则

- 默认中文标题，保留代码标识符原文。
- 格式优先使用：`<type>: <简洁说明>`。
- type 参考：`fix`、`feat`、`refactor`、`docs`、`test`、`chore`。
- 标题描述用户可感知的问题或主要行为变化，不写泛泛的“优化代码”。

## 正文规则

- PR 正文只写 reviewer 需要知道的内容。
- 默认正文格式固定为 `## 变更内容` + bullet 列表。
- 每个 bullet 写真实改动点，不写泛泛收益或内部确认过程。
- 不要写无价值验证项，例如：
  - `已确认工作区干净`
  - `本次改动范围仅限某文件`
  - `未运行测试`，除非这是 reviewer 必须知道的风险
- 不要为了格式完整硬塞 `验证`、`影响范围`、`背景`。
- 如果没有实际运行测试，就不要伪装成验证；必要时只写一句：`未运行自动化测试。`
- 如果已运行测试或构建，才追加 `## 验证`，并只写真实命令和结果。

## 推荐正文形态

### 小修复

```markdown
## 变更内容
- 订阅页出现时，如果商品列表为空，会兜底重新请求价格
- 商品列表更新后继续默认选中年度订阅
```

### 有真实验证

```markdown
## 变更内容
- 订阅页出现时，如果商品列表为空，会兜底重新请求价格
- 商品列表更新后继续默认选中年度订阅

## 验证
- `xcodebuild ... build` 通过
```

### 多模块改动

```markdown
## 变更内容
- 订阅页出现时为空则重新请求商品
- 保留商品异步返回后的默认选中逻辑

## 验证
- `xcodebuild ... build` 通过
```

## 创建 PR 约束

- 不自动编造测试、构建、人工验证结果。
- 不把 `git status` 干净当作 PR 验证内容。
- 如果只能确认提交范围，内部自己确认即可，不写进正文。
- PR 创建完成后只返回 PR 链接、分支和必要说明。
